## 1. 每日建议现在长什么样（先看这个，再看端点）

### 1.1 用户每天实际收到的形态

最短一天是**一行**，最长一天是**四行**。真实形态（匿名化，仅保留结构）：

```
📈 盘前 M/D
{CODE} {简称} 现价{P} → 买(触发{P},入场区{P}-{P},止损{P},止盈{P})
⚠️ 接近: 简称A(距卖1.3%), 简称B(距买0.3%)
其余 N 只观望
基于历史回测,不构成投资建议;开盘前以实时行情为准
```

上游脚本（`trade_preopen_alert.py`）喂给 agent 的原文再富一点，每条标的是三行：

```
**{CODE} {简称}** 现价{P} 动作【hold】 置信{c}%
  - {一句话依据}                      ← action_reason[0]
  - {买/卖信号已触发: 指标 触发价 {P}}   ← triggers[].state / buy_price / sell_price
  - 入场区 {P}–{P} | 止损 {P} | 止盈 {P}
```

5 个交易日实测，**每一行都在说同一件事**：价格在哪、信号触没触发、买卖价位在哪。
从没有出现过的：**仓位多少、拿多久、大盘怎么样、贵不贵、有没有雷、数据是哪天的**。

### 1.2 关键对照：CLI JSON 已经有、建议里没有

## 3. Top 8 下一轮候选

排序原则：**先零取数成本（把已有字段送到用户眼前），再单请求全市场，最后逐票预计算**。

### T1 — 补齐「仓位 / 持有期 / 复审日」三段（缺口表 #1）· P0

- **验收标准（可测）**：给定一份含 `position_fraction=0.15 / horizon_days=[20,20] / review_date` 的 fixture JSON，渲染输出必须匹配 `建议仓位 15%`、`持有 20 日`、`{review_date} 复审` 三段；`position_fraction=None` 时该段**整段消失**而不是打印 `None`。同一批标的连跑两次，输出 diff 仅出现在数值上；`cli.py --json` 逐键不变（现有 schema 兼容测试不回归）。
- **依赖**：无（字段已在 `recommendation` 内）；改动面在消费层（Hermes 提示词 / 渲染），不碰 `decision/actions.py`。
- **风险**：仓位是「策略建议权重」不是「用户该买多少」，措辞必须写「建议仓位」并给免责，否则会被当成下单指令。

### T2 — 可执行性闸门 + 数据新鲜度前置（缺口表 #2）· P0

- **验收标准（可测）**：三个 fixture（停牌 / 一字板 / ST）分别断言建议首行出现 `不可执行` 与具体原因，且 `action` 字段**未被改写**；第四个 fixture（`quote_stale=true`）断言输出出现 `收盘为 {D}` 且不再写「现价」；`diagnostics.warnings` 非空时必须以 `⚠️ 数据:` 前缀出现在**建议之前**（issue #1 的「先报问题再报建议」）。
- **依赖**：`instrument.*` 已由 P0-3 产出；ST 名单当天是否可用（实测正失败，需先修 `§6.8` 的空表判定）。
- **风险**：盘前 09:15 的报价语义是「昨收 + 集合竞价前」，`is_suspended` 在盘前本就可能是 `None`（`status.py` 已显式如此设计）——文案必须区分「确认停牌」与「盘前无法判断」，否则会把正常标的误标不可交易。

### T3 — 指数 regime 与个股 regime 的冲突提示（缺口表 #3）· P0

- **验收标准（可测）**：fixture 个股 `Bull/0.7` + 指数 `Shock/0.5` → 输出出现 `大盘逆风` 一行；两者一致时该行不出现；指数取数失败（`market_regime.index` 缺失）→ 整行消失且不报错。
- **依赖**：`market_regime.index`（已接，`tencent_index:sh000300`）。
- **风险**：这是把「个股自身均线」和「指数环境」两个口径并列，**不是**修改 regime 定义（那是行为变更，需单独 PR）；文案不能暗示「因此不要买」。

### T4 — 估值分位一句（缺口表 #4）· P0

- **验收标准（可测）**：fixture `pe_percentile_3y=12.46` → 输出 `PE 分位 12%（3 年）`（四舍五入规则写进测试）；`available=false` 或 `reason='cache_missing'` → 整句不出现，且**不得**出现「估值适中」这类无数据结论；`percentile_samples.pe < 756` 时文案加 `（样本 {n} 日）`。
- **依赖**：18:40 预计算已跑（实测缓存有效，`rows=2638`）；`baostock` 未写进 `requirements.txt`，需要补声明或改为可选 extras。
- **风险**：PE 分位对周期股/一次性损益会失真；必须带「3 年」窗口和「TTM」口径标签，否则会被当成绝对贵贱。

### T5 — 资金流方向一句 + 口径标签（缺口表 #5）· P0

- **验收标准（可测）**：fixture `direction='outflow', main_net_5d<0` → 输出 `主力 5 日净流出`；同一测试断言输出含 `caliber` 标签（东财 / 新浪必须可区分），**混源时不出现净额数值**只出现方向；`stale=true` → 整句带 `（{D}）` 日期且不参与任何「买入」措辞。
- **依赖**：18:30 预计算（东财 `push2his` + 新浪备胎，已有口径隔离）。
- **风险**：东财资金流字段口径会变；20 日尺度上资金流的解释力弱（这一点必须在文案上保持「描述事实」而非「预测」）。

### T6 — 全市场风险快照：§8.4 监控池（缺口表 #6）· P1

- **验收标准（可测）**：mock 一次约 16 行的监控池 JSON，断言 10 只标的里命中的那几只出现 `🚫 重点监控` 且带生效窗口；接口失败 → 只丢这一行，**不影响**其余建议（禁止整轮静默）；`MARKET='B'`（北交所）样本必须标 `BJ` 而不是 `SZ`（上游明确的三值坑）。
- **依赖**：`em_get()` 串行限流；**一次请求服务全池**，无需逐票。
- **风险**：池子通常只有十几只，命中率低 → 容易变成「永远不出现」的死代码；验收里必须包含一条「人为注入命中」的用例，否则无法证明链路通。

### T7 — 事件风险预计算（§3.6 解禁 / §14.3 增减持 / §14.1 业绩预告 / §14.5 质押）（缺口表 #7–#10）· P1

- **验收标准（可测）**：事件窗口 fixture（解禁日 T+5、减持公告 T-2、预告 T-1、质押比例更新日）→ 逐条断言出现对应行；无事件时零输出；**预计算失败时必须是 `stale=true` + 文案标注「事件数据过期（{D}）」**，不得静默当成「无事件」。
- **依赖**：东财 `datacenter`（与 `push2` 不同风控面），走 `em_get()` ≥1s 间隔；沿用 `precompute_flow.py` / `precompute_valuation.py` 的「写缓存 → 盘前只读」模式（18:30–18:50 已有时段）。
- **风险**：①限流——10 只 × 4 端点 = 40 请求，串行 ≥1s 即 ≥40s，**绝不可放在 09:15**；②「无事件」与「接口坏了」必须分开（上游对个股条件返回空表，全市场 0 行才抛错）；③warning 疲劳——四类事件全开会让每条建议都带感叹号，需要「只报 20 日内 + 只报重大额度」的阈值。

### T8 — 腾讯报价的量比/换手/市值（缺口表 #11）· P1

- **验收标准（可测）**：mock 报价 → 输出 `换手 {t}%`；`is_stale=true` → 不输出量比/换手，且整条降级为「昨收口径」；与现有 `status.py` 的报价缓存复用同一次请求（断言 HTTP 调用次数不增加）。
- **依赖**：腾讯 `web.sqt.gtimg.cn`（**不封 IP**，WAF 冷却期照常可用）；报价缓存已有。
- **风险**：盘前量比恒为 0/空（当日尚无成交）——**这是本项目最容易踩的语义坑**：盘前用「昨日量比」必须显式标注，否则用户会以为是今日。

## 5. 盘点发现的最大缺口

**不是缺端点，是「数据到了库里，没到建议里」——而且这个断层刚好切在 80% 的实仓上。**

三条并列的证据：

1. **交付契约已经写好了，建议没兑现。** issue #1 的验收指标原文是「Hermes 能用『名称（代码）| 收盘 | 建议 | 买入区/止损/目标/**仓位**/**持有期**』一行说清，并说明依据」。实测的每日建议里，**仓位、持有期、依据**三项全缺，而 `position_fraction`、`horizon_days`、`review_date`、`side_expectancy`、`invalidation` **都已在 JSON 里**。这不是取数问题，是消费层的漏接。
2. **19 个 PR 的数据接入，没有改变任何一个字。** P0-1/2/3、P1-1/2/3 全部落地（腾讯 K 线、官方日历、真实交易状态、估值分位、资金流方向、指数 regime），5 个交易日的建议仍只有「价格 + 触发 + 三个价位 + 置信」。`evidence.valuation.pe_percentile_3y` 这种一句话就能改变判断的数据（实测出现极低分位），从来没有出现过。
3. **接进来的东西，对 8/10 只标的是 `fund_not_supported`。** 实仓 10 只里 8 只是场外基金，而上游 §4.5 资金流、§6.5 估值历史、§1.1 报价、§6.8 ST 名单**全部只覆盖个股**；基金那侧 `instrument.name` 直接等于代码、`board` 被判成 `sz_main`、`price_limit_pct=0.1`（对一个场外基金毫无意义）、`is_suspended` 与 `quote_stale` 全是 `null`。**即使把消费层全部补齐，8 条建议仍然是纯量价。** 前向台账（`forward_ledger_daily.py`）也只覆盖 2 只个股，所以这 8 条连「复盘」都没有。

因此下一轮的排序不是「接更多端点」，而是：
① 先把已接字段送进建议（T1–T5，零取数、零限流、当天可测）；
② 再补「一次请求服务全池」的风险快照（T6）；
③ 最后才是逐票事件的收盘后预计算（T7）。
而**场外基金的外部证据**（净值确认时点、申赎费率、同类排名、基准指数）**上游不提供**，这一块是 issue #1 之外的独立课题，不应塞进本轮 a-stock-data 的 backlog。
